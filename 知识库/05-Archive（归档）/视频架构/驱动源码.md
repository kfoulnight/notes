
**simpledrm**
核心思想：显示控制器已经被boot loader初始化好了，内存里已经有一块帧缓存，驱动只做一件事情，把这套现成的硬件，包装成标准的DRM/KMS接口交给用户态。

simpledrm_device_create创建DRM/KMS的核心对象关系，在这个驱动里就是一行行init搭建起来的。
控制链路：
probe：把boot loader留下来的设备接管过来。
	分配drm_device 
	保电时钟：不主动管理，电源管理代码会认为这些时钟没人用，就会导致显示引擎停摆，屏幕黑掉。
	保持电压：
	解析几何参数：从platform_data或DT读取width/height/stride/format
	夺取帧缓存地址空间：
	显存映射：

数据链路：
用户画到 SHMEM 影子缓冲 → 按脏矩形 blit + 格式转换 → 写到 screen_base → 硬件自己扫出去
关键一步数据链路的心脏,四件事：
1：缓存同步 -- 保证CPU写的内容对“读他去显示”可见。
2：damage 迭代(脏矩形遍历)，只更新画面上变化的小矩形，而不是整屏拷贝。
3：算偏移+拷贝/转化，把每个脏矩形换算成 screen_base 里的字节偏移,再 drm_fb_blit 从影子缓冲拷到真实显存,顺手做像素格式转换(比如用户态用 XRGB8888,硬件是 RGB565 —— 这就是 formats[] 数组和 drm_fb_build_fourcc_list 存在的原因)。
4：关闭缓存访问。


DRM/KMS的对象模型：一个最小驱动必须有的四件套，plane(主平面) → CRTC(定时/扫描) → encoder(信号) → connector(物理接口),通过 init_with_planes、attach_encoder 串成管道。看任何 DRM 驱动,先找这四行的 drm_..._init 就抓住了骨架。


**RKdrm**

RK是一个master+n个子驱动的component多驱动架构，simpledrm是一个平台驱动搞定一切。

每个子驱动是一个独立的platform driver，各自probe时调用component_add,master用 component_master_add_with_match  等所子驱动都注册就绪后，才执行真正的rockchip_drm_bind。

masterprobe 扫ports属性 确认有VOP ->rockchip_drm_match_add把每个子驱动设备加入 match->component_master_add_with_match。

bind时依次调用每个子驱动的.bind。

**控制链路：**
RK的VOP就是CRTC，一颗完整的显示控制器硬件，有寄存器、有中断、有电源域、有独立的时钟树。
提交时的控制动作：VOP的CRTC钩子表，里面有 ：
.atomic_check → 检查 mode 是否超 VOP 能力(分辨率/时钟/色深)
.atomic_enable → 打开电源域、配时钟(dclk 按模式算)、写时序寄存器(htotal/vtotal/同步信号) .atomic_flush → vop_cfg_done():写"配置生效"位,让 VOP 在下一个 vblank 锁存新配置 .atomic_disable → 关时钟、关窗口、standby

VOP注册了硬件中断。

编码器/连接器：rk的HDMI/DP/DSI是独立子驱动，支持热插拔，- 链路训练(DP)、DSC 压缩(HDMI 2.1)、色深/色彩空间协商;- connector 通过 rockchip_drm_register_sub_dev注册进全局 sub_dev 链表,供 VOP 反查(比如 DSI 面板的 TE 信号、VRR 的 vfp 调整)。

**数据链路：**
VOP的vop_plane_atomic_update一行像素都没有搬运，他写的是窗口寄存器，告诉VOP去哪读内存，怎么缩放，怎么混合。
异步更新

用户态渲染到GEMbuffer->显存中的frame buffer（DMA地址）->VOP硬件DMA引擎在vblank锁存新配置（cfg_done）->输出接口（HDMI/DP/DSI....）->屏幕。



3576用的是VOP2 
差别在于VOP2是多视频端口+窗口池+动态路由，一个VOP2硬件能够同时当作4个CRTC使用，窗口资源跨屏幕自由分配。

在KMS模型里，plane是池子，CRTC是出口，池子共享，出口多个。（DRM本身允许同一个plane被多个CRTC共享）

一个 VP/CRTC 在同一时刻确实只驱动一条输出通道,但"占据"不是物理焊死的,而是软件路由出来的。
从DRM链路来看一个CRTC同一时刻只连接一个encoder，模型规定死的。
限定一：VP 这次 modeset 可以路由到 HDMI,下次可以改到 eDP——"占据哪条通道"每次提交时重配,而不是硬件固定死了。
限定二：通道数<=VP数量，而且有mux冲突，接口往往比VP多，但是同一时间能同时点亮的通道数最多=活跃VP数（<=4）,而且有些接口会互斥（共享同一个mux位域）。所以不是有4个VP就能开4个任意接口，还要看组合有没有冲突。
限定三：splice模式是两个CRTC抢一条通道，比如>4096像素宽（比如8K）时，一条输出通道通常要2个VP拼一起来扫。
